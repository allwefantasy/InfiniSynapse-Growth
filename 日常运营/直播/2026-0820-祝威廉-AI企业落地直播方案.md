### 参考演示案例（来自 8/1 技术交流纪要）

现场核心不是「先建数仓再问数」，而是：**未治理直连 → 自然语言提问 → 自动探表/出结果 → 每步 SQL 与血缘可核验 → 口径纠错后沉淀复用**。

| 段落 | 演示做了什么 | 对企业观众意味着什么 |
| --- | --- | --- |
| 主 Demo | 同时连接 **PG + MySQL**，**未做任何治理**，直接问「统计两个数据源中最畅销商品」；AI 自动探索库表、生成中间表、输出结果，并展示**数据血缘**和每一步 SQL | 不用先自建数仓；多源联邦分析；结果可人工复核 |
| 口径 Demo | 先跑一个算错的「有效活跃用户」；补充业务口径后重算正确，并把正确口径**自动沉淀到业务中心**，后续同类问题可复用 | 解决企业最痛的 Source of Truth：AI 与人对齐 |
| 性能答疑 | 生产库大、表差、直连怕压库 → 可用知识库冷启动加速；压力大则同步到 ClickHouse 等引擎，SQL 下推 | 医院/企业业务库也能落地，不是只能演示库 |
| 权限口径 | 产品支持到**库级权限**；表级/数据级建议由上层应用控制 | 企业落地时权责边界说清楚 |
| 可复用旁证（口播一带，不现场重跑） | 海关评分卡：92 秒完成特征工程+训练，AUC 0.77（高于人工 XGBoost 0.76）；零售补货、CDN、企名片等 | 证明不只是问数，也能走到建模/业务应用 |

技术要点（口播可用，少堆术语）：自研分析语言（非 Python 沙箱）、多源联邦、知识库绑数据源、Context Hub 对齐口径、层级结果 + 实时血缘。
