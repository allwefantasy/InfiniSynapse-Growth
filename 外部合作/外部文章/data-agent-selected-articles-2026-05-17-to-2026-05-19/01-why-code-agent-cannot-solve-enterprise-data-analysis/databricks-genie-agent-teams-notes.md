# Databricks Genie 与 Agent Teams 备忘

来源文章：

- Databricks Blog, [Pushing the Frontier for Data Agents with Genie](https://www.databricks.com/blog/pushing-frontier-data-agents-genie), 2026-05-08.

关联文章：

- `article-v2.md` / `article-v2-en.md`：为什么 Code Agent 无法解决企业数据分析问题

## 核心信息

Databricks 这篇文章里值得单独记下的，不只是 Genie 本身，而是它把企业级 Data Agent 的能力拆成了几个很清晰的系统环节：

1. 并行多代理数据发现
2. 数据调查
3. 自我纠正循环
4. 验证

这四点可以直接映射到 InfiniSynapse 的 agent teams 表达里。

## 1. 并行多代理数据发现

并行多代理数据发现对应我们的 **agent teams** 功能。

企业数据分析的第一个难点，往往不是写 SQL，而是快速判断：

- 数据可能在哪些库里；
- 哪些表、视图、指标、报表、历史分析资产可能相关；
- 是否存在多个业务口径；
- 是否需要同时查看结构化数据、文档、知识库和历史查询。

单个 Agent 顺序探索会很慢，也容易被第一个看似合理的数据源带偏。agent teams 的价值在于让多个 Agent 实例从不同维度并发探索可能的数据源，例如：

- 一个 Agent 查数据库元数据和表结构；
- 一个 Agent 查查询历史和指标口径；
- 一个 Agent 查绑定知识库、业务文档和说明；
- 一个 Agent 查历史报表、dashboard 或 notebook；
- 一个 Agent 专门寻找反例、冲突口径和缺失字段。

这不是简单的“多开几个线程”，而是让系统在早期就获得多视角、多实例、快速并行的数据发现能力。

## 2. 数据调查

数据发现之后，还需要更细的数据调查。

这里的重点不是马上生成答案，而是仔细查看各类数据源以及查询绑定的知识库，拿到足够多的上下文细节：

- 表与字段的真实业务含义；
- 字段取值范围、缺失情况、异常值；
- 指标口径和过滤条件；
- 不同系统之间的主键、外键或业务关联；
- 相关知识库里对口径、流程、组织、产品、客户、时间周期的解释；
- 历史查询或历史报表里隐含的惯用写法。

这个阶段同样适合用 agent teams 承担。不同 Agent 可以分别调查不同数据源、不同业务域或不同假设，再把调查结果汇总给主 Agent。这样既能提高速度，也能减少单一路径探索造成的误判。

## 3. 自我纠正循环

自我纠正循环是 agentic 范式里的基本能力。

Data Agent 不应该把第一次生成的 SQL、第一次读到的字段说明、第一次得到的查询结果直接当成最终答案。它需要持续检查：

- 查询是否跑通；
- 结果是否符合常识和业务约束；
- 是否存在空结果、重复计数、口径错用或时间范围错位；
- 是否需要换表、补充 JOIN、调整粒度或重新理解问题；
- 当前证据是否足够支持结论。

如果发现问题，Agent 应该回到前面的数据发现和数据调查阶段，重新选择数据源、修改查询或补充证据。这是 Data Agent 区别于一次性 Text2SQL 的关键。

## 4. 验证

验证是企业级数据分析能否被信任的最后一环。

一个可落地的 Data Agent 不能只给出自然语言答案，还应该尽量说明：

- 使用了哪些数据源；
- 采用了什么指标口径；
- 查询或计算路径是什么；
- 结果是否经过交叉检查；
- 哪些结论是确定的，哪些仍然依赖假设；
- 哪些数据缺失、口径冲突或权限限制会影响可信度。

验证可以由主 Agent 执行，也可以交给专门的 agent teams 成员从审计、业务口径、数据质量、反例搜索等角度并行检查。

## 对 InfiniSynapse 的表达

可以把这四点浓缩成一句产品表达：

> InfiniSynapse 的 agent teams 让多个 Data Agent 实例围绕同一个业务问题，并行完成数据发现、数据调查、自我纠正和结果验证，从而在复杂企业数据系统中更快找到可信答案。

更偏销售或演示的表达：

> 遇到复杂数据问题时，用户不需要手工指定所有库表。只要在 prompt 里提到 agent teams 或 subagent，InfiniSynapse 就可以触发多 Agent 协作：先并行探索可能的数据源，再调查绑定知识库和字段口径，然后在查询执行中持续自我纠正，最后对答案做验证和说明。

## 触发方式

触发 agent teams 的方式保持简单：

- 在 prompt 中直接提及 `agent teams`；
- 或者提及 `subagent`。

系统即可理解用户希望启用多 Agent / 子 Agent 协作模式，用于多维度、多实例、并发探索和验证。
