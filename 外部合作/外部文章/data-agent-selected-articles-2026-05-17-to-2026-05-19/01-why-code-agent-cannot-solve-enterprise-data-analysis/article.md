# 为什么 Code Agent 无法解决企业数据分析问题

## 第一篇：数据分析不是写代码，而是生产可信答案

这两年，很多人对 Code Agent 的能力产生了一种很自然的错觉。

他们打开 Claude Code、Codex 或 Cursor，把一个 Excel 拖进去，让 Agent 写几段 Python，跑一轮 pandas，画几张图。效果看起来很好。再进一步，Agent 还能通过工具连接数据库，执行 SQL，甚至把多个数据源的结果拼到一起，生成一个 dashboard。

于是一个问题就出现了：

> Code Agent 已经能分析 Excel，也能连数据库，为什么还需要专门的 Data Agent？

这个问题表面上是在问产品形态，实际上是在问一个更底层的问题：

> 数据分析到底是不是一种编程任务？

我的答案是：在轻量场景里，它可以被临时包装成编程任务；但在企业场景里，它本质上不是编程任务，而是一个“可信答案生产系统”。

这正是 Code Agent 无法真正解决数据分析，尤其是企业数据分析的根本原因。

Code Agent 的目标函数是“把代码写出来，并让它跑起来”。Data Agent 的目标函数是“找到可信数据、理解业务语义、执行正确分析、留下可复核证据，并在不确定时承认不可回答”。

这两个目标函数看起来相近，但只要进入真实企业现场，就会迅速分叉。

---

## 一、Code Agent 的强大，反而暴露了它的边界

先说清楚，我并不否认 Code Agent 的能力。

Code Agent 在它擅长的领域非常强：

- 它能读代码库，理解函数、文件、依赖和测试；
- 它能修改代码，运行测试，根据报错继续修；
- 它能快速写脚本，处理一次性的文件清洗；
- 它能把 CSV、Excel、JSON 这类小数据喂给 pandas，快速做探索；
- 它能生成漂亮的页面和 dashboard。

这些能力是真实的，也确实有价值。

问题在于，Code Agent 做数据分析时，通常会把数据问题转译成代码问题：

> 用户问一个业务问题，Agent 写一段 Python 或 SQL，跑出结果，再根据用户追问继续改代码。

在前几轮，这个过程很顺。到了第 10 轮、第 20 轮，问题开始变质。

代码会越来越大。变量会越来越多。中间 DataFrame 会被覆盖、复制、重命名。为了兼容某个异常，Agent 加一个 `try/except`。为了画一张图，Agent 引入一个包。为了修一个类型错误，Agent 又加一段转换逻辑。为了连接另一个数据库，Agent 开始纠结驱动、版本、连接串、认证方式。

最后你会得到一坨“能跑”的代码。

但数据分析最可怕的地方就在这里：

> 能跑，不等于对。

复杂代码本来就是反人类的。它对于人类难读，对于 Agent 也难维护。代码越大，Agent 越容易把注意力花在工程细节上，而不是业务逻辑上。它开始关心包有没有装、字段类型怎么转、API 参数叫什么、内存会不会爆，而不是关心“这个 GMV 口径到底是不是业务真正认可的口径”。

这不是某个模型不够强，而是范式错了。

## 二、数据分析的核心不是执行，而是可信

写代码的闭环相对清楚：

1. 需求是什么；
2. 改哪些文件；
3. 运行测试；
4. 测试失败就修；
5. 测试通过，基本可以认为行为至少符合某种规格。

数据分析没有这么幸运。

用户问：

> 上季度华东地区的收入为什么下降？

这里没有一个单元测试告诉 Agent 答案对不对。甚至“上季度”“华东”“收入”“下降”这四个词本身都可能有多种解释。

收入是订单金额，还是确认收入？是含税还是不含税？退款要不要扣除？华东地区按收货地址算，还是销售组织算？上季度按自然季度，还是财务日历？异常下降是同比、环比，还是预算偏差？

企业数据分析的难点从来不是“写一条 SQL”。真正难的是：

- 找到应该信任的数据资产；
- 判断相似表之间的口径差异；
- 理解业务词在当前公司的真实含义；
- 把结构化数据和业务文档里的非结构化知识对齐；
- 在缺失数据、冲突定义和脏数据里保持谨慎；
- 留下每一步计算和判断的证据；
- 让业务、数据、审计和 IT 都能复核。

Databricks 在 2026 年 5 月 8 日发布的 Genie 文章里，其实也给了同样的信号。他们把 Data Agent 的挑战描述为一个动态、持续变化、充满语义上下文的数据系统，而不是一个静态文件系统。文章还提到，在内部真实数据分析任务 benchmark 上，加入 specialized knowledge search、parallel thinking 和 Multi-LLM 之后，Genie 相比领先 coding agent 从 32% 提升到 90% 以上。这是 Databricks 自己的内部实验结果，但方向很清楚：企业数据问题不能只靠通用 Code Agent。

真正的 Data Agent 不是“会写代码的模型”，而是“能在企业数据语境里生产可信答案的系统”。

---

## 三、Code Agent 会把探索过程不断覆盖掉

数据分析不是一次性问答，而是连续追问。

一个真实分析通常长这样：

1. 先看整体收入趋势；
2. 发现某个区域下降；
3. 按行业下钻；
4. 找到某类客户异常；
5. 对比去年同期；
6. 检查是否有价格政策变化；
7. 关联销售活动；
8. 排除节假日、汇率、数据延迟；
9. 重新计算净收入；
10. 形成结论和风险提示。

这不是“写一个脚本”能自然承载的工作流。

Code Agent 的默认方式是持续修改代码。第 3 步会改第 1 步的变量，第 6 步会追加一段 merge，第 8 步会覆盖之前的过滤条件，第 10 步再把前面的若干逻辑揉成一个最终版本。

结果是，中间过程很难留痕：

- 第一次为什么选这个表？
- 第二次为什么改了过滤条件？
- 第三次为什么排除了退款？
- 哪一步发现字段含义有问题？
- 哪个中间结果支撑最终结论？
- 如果下周重新跑，能不能得到同样的分析轨迹？

代码最后可能还在，但探索过程已经被不断改写。

这就是 Code Agent 做数据分析最大的问题之一：它把“探索”压缩成“最终代码”。而企业数据分析真正需要的恰恰是探索过程本身。

因为企业要的不只是答案，还要知道答案是怎么来的。

---

## 四、企业数据不是一个文件夹，而是一个异构现场

Code Agent 之所以能改变编程，是因为代码库天然适合它。

代码大多在文件系统里。文件有路径。函数有名字。依赖有声明。测试可以运行。Git 可以追踪变更。虽然工程很复杂，但它至少处在一个相对确定的系统里。

企业数据不是这样。

企业数据分散在很多地方：

- MySQL 里的业务订单；
- PostgreSQL 里的运营数据；
- ClickHouse 里的事件日志；
- Hive 或 Spark 里的历史明细；
- Excel 里的临时报表；
- API 里的实时状态；
- PDF、Word、飞书文档里的业务说明；
- dashboard 和 notebook 里的历史分析逻辑；
- 人的习惯和部门约定里的隐性口径。

它们不在一个文件夹里，也不服从同一种版本控制。很多数据是动态变化的，很多语义不写在 schema 里，很多指标的真实定义只存在于文档、历史分析和团队共识里。

这就是为什么“让 Code Agent 连多个数据库”并没有真正解决问题。

连接只是第一步。真正的问题是：

- 它知道哪张表是权威表吗？
- 它知道这个字段什么时候开始改过口径吗？
- 它知道某个 dashboard 为什么和另一张报表数字不一致吗？
- 它知道 Excel 里的临时口径能不能和生产库字段 join 吗？
- 它知道哪些数据能出现在报告里，哪些数据只能内部使用吗？

如果不知道，它只是把多个不确定来源拼在了一起。

多个数据库 join 在一起，不自动等于企业数据分析。很多时候，它只是更复杂、更难发现错误的“错误答案生成器”。

## 五、给 Code Agent 加数据库连接，仍然绕不开三件事

有人会说，既然 Code Agent 写 pandas 有问题，那就让它直接写 SQL，让它通过工具连接数据库，不就好了？

这确实能改善一部分问题，但仍然绕不开三件事。

第一，Code Agent 仍然会回到工程问题上。

它要处理数据库驱动、连接方式、网络、权限、依赖、SQL 方言、结果分页、类型转换、超时重试、临时文件和本地内存。Agent 的注意力还是会被工程细节占用。

第二，它缺少稳定的分析状态层。

普通 SQL 的结果通常是一次性的。Code Agent 要复用中间结果，就要创建临时表、写 CTE、缓存 DataFrame，或者在脚本里自己维护变量。随着追问增加，状态管理仍然会变成代码管理问题。

第三，它没有业务语义绑定。

数据库连接告诉 Agent “数据在哪里”，但没有告诉它“这个数据意味着什么”。schema 只能解释字段名和类型，不能解释计算口径、业务事件、指标边界、使用禁区和历史变化。

所以，Code Agent 加数据库连接，只是让它从“写本地脚本”变成“写远程脚本”。它没有把数据分析从编程问题还原成分析问题。

## 六、为什么企业数据分析必须有自己的 Agent 语言

这是 InfiniSynapse 选择 InfiniSQL 的根本原因。

我们不是让 AI 在 Python、驱动、并发、封装、环境、依赖和数据库连接细节里打转，而是给 Agent 一门更适合数据分析的工作语言。

InfiniSQL 的重点不是“又一种 SQL 方言”，而是把 Agentic 分析需要的结构做成语言约束。

最关键的是 `select ... as tableName`。

每一步分析都必须产出一张具名表：

```sql
select region, sum(amount) as revenue
from orders
group by region
as region_revenue;

select *
from region_revenue
where revenue < 0
as abnormal_region_revenue;
```

这段代码对应的不是“一次写完的脚本”，而是 Agentic 工作流里的两次工具调用。

第一次工具调用产出 `region_revenue`，把原始订单数据抽象成“按地区汇总后的收入表”。第二次工具调用直接基于 `region_revenue` 继续分析，筛出异常地区，产出 `abnormal_region_revenue`。

随着工具调用次数变多，InfiniSQL 的 session 里会逐渐沉淀出一批经过探索、清洗、聚合和命名的中间表。它们共同形成一个面向当前问题的“虚拟数仓”。这个虚拟数仓不是事先由数据团队建好的，而是在 Agent 的分析过程中自然生长出来的。

这会让后续分析变得越来越容易。因为 Agent 不再每次都回到原始明细表重新理解数据，而是可以站在已经高度抽象、已经带有业务含义的中间表之上继续追问。

这个设计看起来小，但对 Agent 极其重要。

它意味着：

- 每一步都有名字；
- 每一步都能被后续引用；
- 每一步都能被人检查；
- Agent 不需要维护一堆 Python 变量；
- 追问不是回头改旧代码，而是追加新的分析步骤；
- 一次分析天然形成可回放的数据探索轨迹。

这就是 Agent 友好语言和人类脚本语言的差别。

Python 是给程序员的。pandas 是给数据科学家的。普通 SQL 是给数据库和分析师的。InfiniSQL 是给 Agent 的。

它让 AI 专注于声明式 SQL 业务逻辑，而不是纠结并发、封装、驱动版本、运行环境和本地内存。

## 七、异构数据源 Join 不能靠“拉到本地再 merge”

企业数据分析里，异构数据源是常态。

一个看似简单的问题，可能需要同时用到：

- 订单库；
- 客户库；
- 运营活动 Excel；
- 产品埋点日志；
- 外部行业数据；
- 内部政策文档。

Code Agent 的自然做法是把数据拉出来，变成 DataFrame，然后 merge。

这在小数据 demo 里很好看，在企业数据里很危险：

- 数据量一大，本地内存撑不住；
- 数据一拉出生产环境，合规和审计压力立刻上升；
- 大量计算没有下推到数据库或分布式引擎；
- 跨源 join 的结果很难复核；
- 中间文件和缓存容易变成新的数据泄漏面。

InfiniSQL 选择的是另一条路：让异构数据源在同一个 session 里以表的形式共存，让跨源 Join 成为语言和引擎层的原生语义。

```sql
connect jdbc where url="mysql://..." as mysql_biz;
connect jdbc where url="postgresql://..." as pg_ops;

load jdbc.`mysql_biz.orders` as orders;
load jdbc.`pg_ops.customers` as customers;
load excel.`/data/campaign.xlsx` as campaign;

select o.order_id, o.amount, c.level, campaign.channel
from orders o
left join customers c on o.customer_id = c.id
left join campaign on o.campaign_id = campaign.id
as order_customer_campaign;
```

这里的关键不只是“能 join”，而是 Agent 不需要从分析师变成数据工程师。

它不需要自己决定怎么拉取、怎么缓存、怎么分页、怎么处理内存。它只要表达业务关系，引擎负责执行细节。

这才是企业数据分析应该给 Agent 的抽象层。

## 八、InfiniRAG 解决的是业务语义，不是“多塞一点上下文”

很多人把 RAG 理解成“把文档搜出来塞给模型”。这对企业数据分析远远不够。

企业里的业务知识不是装饰性上下文，而是分析本身的一部分。

比如一个字段叫 `metric_key`，数据库只能告诉你它有哪些取值，出现了多少次。它不能可靠告诉你：

- `DOWNLOAD` 是下载意图，还是确认安装；
- 某个 key 属于 Office 自动化，还是开发者工具；
- 某个状态代表失败，还是等待人工处理；
- 某个指标是否适合对外发布；
- 哪个漏斗口径是当前业务认可的版本。

这些信息通常在文档、数据字典、历史报告、产品说明、团队习惯和个人偏好里。

InfiniRAG 的价值不是“找几个片段给模型看”，而是把业务知识、个人偏好、计算口径、库表元信息、历史分析和外部信息变成 Agent 可以调用、可以验证、可以与数据源绑定的知识层。

一句话：

> 数据库告诉 Agent 发生了什么，知识库告诉 Agent 这件事意味着什么。

这也是结构化数据和非结构化数据的互补式绑定。

结构化数据负责可计算事实。非结构化知识负责业务解释、口径边界和判断依据。两者分开，Agent 会变成“会查数但不懂业务”的工具。两者绑定，Agent 才有机会成为真正的数据分析师。

更重要的是，知识库不能只是会话外的一堆资料。它必须进入执行链。

严肃的 Data Agent 应该能在写 SQL 前先问知识库：

- 这个指标应该怎么定义？
- 这个字段有哪些业务禁区？
- 这个状态应该如何归类？
- 过去类似问题是怎么分析的？
- 用户偏好什么样的图表和报告结构？

然后再用 SQL 去验证可计算事实。

这才是业务知识和数据计算的正确关系。

## 九、企业要的是可审计工作流，不是一次性答案

Code Agent 最容易给出的是“最终答案”。企业真正需要的是“可审计的分析工作流”。

一个合格的企业 Data Agent 至少要留下这些东西：

- 使用了哪些数据源；
- 查询了哪些表；
- 每一步生成了什么中间结果；
- 使用了哪些业务口径；
- 哪些结论来自数据库事实；
- 哪些解释来自知识库；
- 哪些地方存在不确定性；
- 最终报告对应哪些 SQL、图表和文件；
- 后续是否可以重新运行、复核和复用。

这也是 InfiniSynapse Task View、SQL 轨迹、具名表、图表、文件和报告这些设计存在的原因。

企业不是不相信 AI。企业是不相信没有证据链的 AI。

Data Agent 要进入企业，必须从第一天起就把“留痕、复核、回放、复用”做进产品结构里。

这不是 UI 细节，而是企业可信系统的底座。

## 十、Code Agent 与 Data Agent 应该协作，而不是互相替代

所以，正确的判断不是“Code Agent 没用”，也不是“Data Agent 会取代 Code Agent”。

更准确的分工是：

| 场景 | 更适合的工具 |
|---|---|
| 写代码、重构、修 bug、生成页面 | Code Agent |
| 小 CSV、一次性 EDA、临时图表 | Code Agent 可以胜任 |
| 多轮追问、业务口径、跨源分析、报告沉淀 | Data Agent |
| 企业数据库、权限、审计、私有化部署 | Data Agent |
| 结构化数据 + 非结构化业务知识联合分析 | Data Agent |
| 严肃决策、监管报告、金融风控、经营分析 | Data Agent |

InfiniSynapse 也没有把 Code Agent 当作敌人。相反，它提供 Command Tools，让 Cursor、Claude Code、Codex、WinClaw 这类 Agent 可以调用 InfiniSynapse 的数据分析能力。

但这里的口径要讲准确：InfiniSynapse 给 Code Agent 生态的触达方式是下载单个二进制 Command Tool，放进 `PATH` 后直接使用。它不是 `pip install` 的 Python 包，也不是让用户自己起一个常驻 MCP 服务。

这背后的产品哲学是：

> Code Agent 继续做它擅长的代码工作，Data Agent 承担它擅长的数据分析工作。

用一个通用 Agent 做所有事情，听起来很诱人，但企业系统的发展规律从来不是这样。通用能力成熟之后，一定会分化出专业系统。

Code Agent 是软件工程的专业系统。Data Agent 是企业数据分析的专业系统。

---

## 结语：问题不是模型够不够聪明，而是工作语言对不对

Code Agent 无法解决企业数据分析问题，不是因为它不聪明，也不是因为它不会写 SQL 或 Python。

根本原因是：它把数据分析放进了编程范式里。

而企业数据分析真正需要的是另一套范式：

- 以可信答案为目标，而不是以代码可执行为目标；
- 以业务语义为核心，而不是以字段名为核心；
- 以多步可回放工作流为载体，而不是以最终脚本为载体；
- 以异构数据源原生联合为基础，而不是拉到本地再 merge；
- 以知识库和数据库绑定为语义 grounding，而不是临时检索几段文档；
- 以权限、审计、部署边界为前提，而不是个人电脑上的自由连接。

这就是为什么 Data Agent 必须有自己的基础设施。

InfiniSynapse 的答案是三件事：

- InfiniAgent 负责规划、小步探索和自我纠错；
- InfiniSQL 负责给 Agent 一门稳定、低错误率、可累积、支持异构 Join 的分析语言；
- InfiniRAG 负责把业务知识、个人偏好、计算口径、历史分析和非结构化信息绑定到数据源上。

三者合在一起，才不是“会写 SQL 的聊天框”，而是一个真正面向企业数据现场的分析系统。

Code Agent 的时代已经证明：当 AI 拥有合适的工作界面，它可以改变软件开发。

Data Agent 的下一步也一样。

关键不在于让 AI 写更多代码，而在于给 AI 一门适合数据分析的语言、一套能理解业务语义的知识系统，以及一条可被企业信任的执行链路。

这才是企业数据分析真正需要的东西。
